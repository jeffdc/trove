When a worker request times out, kill the Go worker process and start a fresh one for later operations.

**The rule** (matter 1f53, Timeout / kill strategy):

The safe boundary is the worker process, not a goroutine wrapper alone.

Rules:

- risky filesystem requests may still have an internal timeout for response purposes
- if the worker reports `timeout`, assume the process may contain leaked goroutines and kill it immediately
- if the OCaml side gets no response in time, kill the worker immediately
- restart a fresh worker for subsequent operations
- persist run state before and after each mutating step so recovery is deterministic

This means timeout recovery is implemented by process replacement plus DB-backed reconciliation, not by trusting the old in-memory worker state.

**What it overrides** (matter 27c2, Task 7: Timeout isolation): Risky operations (copy, move, hash — anything that reads/writes files) run inside a timeout wrapper. Use `context.WithTimeout` + goroutine. If the operation exceeds the per-request timeout (from `args.timeout_seconds`, default 60), the goroutine is abandoned and a `timeout` error is returned. The main worker process stays alive — it's the goroutine that's abandoned, not the process. If the worker itself becomes unresponsive (mount freeze), the OCaml layer detects this via its own response timeout and kills/restarts the worker process. This is simpler than subprocess-per-operation. The worker IS the isolation boundary (it's already a child process). If it hangs, the parent kills it.

27c2's note on that task: The go-port-plan doc discusses subprocess-per-operation. That's overkill for v1. The worker process itself IS the subprocess boundary. If a goroutine hangs on kernel I/O, the OCaml layer kills the worker process and spawns a new one. This matches the "kill and replace the worker on timeout" design without nested subprocesses.

**Reason given:** 1f53: if the worker reports `timeout`, assume the process may contain leaked goroutines. Commit 9b30961: killing and restarting "sheds accumulated leaked goroutines from NAS hangs without requiring changes to the Go side."

**As built** (9b30961 on go-ocaml-rewrite, "Add worker watchdog: timeout, kill, and auto-restart"): Worker_client monitors response time via Unix.select. If the Go worker doesn't respond within response_timeout (default 120s), OCaml sends SIGKILL, cleans up pipes, and transparently restarts the worker on the next call.
